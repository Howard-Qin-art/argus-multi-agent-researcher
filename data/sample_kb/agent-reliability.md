# Agent 系统的可靠性工程

让 Agent 跑通一次不难，难的是在真实负载下持续稳定。可靠性工作集中在四个方向：失败能否自恢复、输出是否结构化可校验、工具调用是否有边界、出问题能否定位。

## 自纠错循环、重试预算与防护

自纠错（self-correction / reflection）的常见实现是：工具或校验抛出异常后，把原始报错回贴给模型让它重写。它对格式错误、参数缺失这类局部错误非常有效。

它的边界同样清楚：如果检索召回本身错了，或对任务理解偏了，模型在同一上下文里反复重写只会原地打转。因此必须区分可自愈错误与不可自愈错误。

重试预算要显式化：全局最大工具调用次数、单节点最大重试次数、连续相同错误的熔断阈值。每次重试都应把上次失败原因写入状态，避免重复犯同一个错。

防无限循环的手段包括：用调用指纹（工具名加参数哈希）识别重复动作并直接熔断；把重试计数作为路由终止条件；给整条链路加墙钟超时。

## 结构化输出校验与降级

依赖模型自由文本输出等于把风险留给自己。主流做法是用 JSON Schema 或 Pydantic 模型约束输出，多数推理服务也支持 structured output 与 constrained decoding 来强制合规。

校验失败后的降级要分层：先做轻量修复（补默认值、类型强转、剥离代码块围栏），再重试一次并要求模型自检，最后才退到保守答复。

还要避免过度严格：枚举值不匹配就整条判失败会让可用率骤降。更好的方式是把字段按重要性分级，非关键字段缺失时填空并记录告警。

## 工具调用的白名单与安全兜底

工具不是越多越好，应按最小权限开放，并维护一份白名单：只允许调用登记在册的工具与参数组合。

以 NL2SQL 场景为例，其做法可迁移到其他高风险工具：生成的 SQL 不直接执行，先解析成 AST 做白名单校验，限定 SELECT、限定表与列、强制行数上限，再用只读连接的账号执行。

同类策略还有：路径类参数限制在允许的工作目录内，外部请求限定域名，写操作要求幂等键并支持回滚，危险操作前置二次确认。

## 上下文压缩与摘要策略

上下文膨胀是长任务最常见的隐性故障源：越往后 token 越多，注意力被稀释，成本与延迟同步上升，而错误信息的回贴会进一步加速膨胀。

常见压缩策略有三种：按轮次滚动摘要、保留最近若干条原文其余摘要、按信息类型裁剪（工具返回只留结构化摘要，原文存档到外部）。

压缩点要选在语义边界而非字节边界，否则会截断表格或半截引用。压缩后应保留痕量字段说明此处已被摘要，便于排障时回溯。

## 可观测性：trace 字段设计

没有 trace 就没有可靠性。每条请求生成 trace_id，每次模型调用与工具调用分配 span_id 与父 span，多轮对话再用 session 维度聚合。

关键字段建议包含：节点名、轮次序号、输入输出 token 数、工具名与参数摘要、耗时、错误类型、重试次数、模型版本与 prompt 版本。参数必须脱敏后再落盘。

有了这些字段才能回答真实问题：成本花在哪个节点、失败集中在哪个工具、哪次 prompt 改动引入了回退，并据此做告警与容量规划。

## 常见误区

- 把无限重试当作高可用：没有预算与熔断的自纠错只会把小故障放大成账单事故。
- 只打印最终答复：缺少工具输入输出的 trace，线上故障几乎无法复现。
- 校验失败就抛异常：缺降级会让可用率远低于模型的真实能力。
- 安全检查放在事后：白名单应前置到参数生成之后、真正执行之前。
