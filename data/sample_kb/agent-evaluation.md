# Agent 评测体系怎么搭

Agent 评测难在两端：最终答案质量需要人来判断，而执行过程又有多条可行路径。只用人工评分不稳定、不可回归；只用自动化硬指标又会漏掉真实体验。可行做法是分层度量并建立可持续跑的回归集。

## 为什么 Agent 评测特别难

与传统 NLP 任务不同，Agent 的输出是一条轨迹（trajectory）：工具序列、中间状态与最终答复都可能不同却同样正确，因此不能用最终串匹配来判定。

人工评审主观性强：不同评审员尺度不一，且随疲劳度漂移。标注一致性通常用 Cohen's kappa 一类指标监控，低于阈值就要回头复核标注规范。

还有成本约束。Agent 单次运行慢且贵，评测集稍大就跑不动，所以采样策略与并行度必须一开始就设计好。

## 硬指标：执行结果与过程正确性

第一类是结果类指标：任务完成率、exact match、字段级 precision / recall / F1，适用于有确定标准答案的场景，例如槽位抽取或工具参数是否正确。

第二类是过程类指标：工具调用序列的集合 F1、必调工具是否调用、冗余调用次数、失败重试次数。它们能解释为什么会错，比单一终点指标更可定位。

第三类是稳定性指标：重复运行的 pass@k 与 pass^k。前者衡量最好一次能否成功，后者衡量能否稳定成功，两者差距往往直接反映系统是否可上线。

## LLM-as-judge 与 rubric 设计

当任务没有标准答案时，常用 LLM-as-judge：由评委模型按 rubric 打分。裸提示让模型直接打个分极不可靠，必须给出逐条 checklist 与明确档位定义。

已知偏差要主动防：位置偏差（偏好第一个候选）、长度偏差、自偏好偏差（倾向自家模型的输出）。做法是打乱候选顺序、做双向互换校验、要求评委先给理由再给分。

还要防评分漂移：模型版本与温度一变分数就不可比。应当固定 judge 的模型快照与解码参数，并保留一批锚点样本长期打分以观察基线漂移。

## 引用与溯源校验

对带检索的问答，引用是否真实比答案本身更要紧。可自动校验的点包括：每条引用片段能否在召回文档中原样命中、引用编号与来源是否对应、携带断言的句子是否真的带了引用。

溯源链路要贯穿全流程：检索块要有稳定 id，写作时按 id 引用，离线评测才能反向定位到具体 chunk，而不是只能看到一句自然语言。

由此还能派生有依据率这类可自动化指标，它与用户感知的可信度高度相关，且几乎不需要人工参与。

## 评测集分层与回归 CI

评测集应按能力维度分层（工具使用、规划、拒答、格式遵循、长上下文），并按难度分层。只报一个总分会把短板掩盖掉。

回归评测要进 CI：每次改动 prompt、路由条件或模型版本都自动跑一遍，并设置阈值门禁。但要区分波动与劣化，通常多次运行取均值并保留置信区间。

工程上还要控制 flakiness：固定随机种子、固定外部依赖版本、给第三方 API 做录制回放，否则测试的红绿没有意义。

## 常见误区

- 只看最终答案正确率：中间工具调用错误但答案碰巧对，上线后迟早暴露。
- judge 与被测系统用同一家模型图省事：自偏好偏差会让分数系统性偏高。
- 评测集长期不更新：反复使用同一批题会造成过拟合，需要定期轮换 held-out 题目。
- 用单次运行结果下结论：Agent 非确定性明显，结论必须建立在重复实验上。
