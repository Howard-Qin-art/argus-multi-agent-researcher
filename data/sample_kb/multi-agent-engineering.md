# 多智能体系统工程实践要点

多智能体系统把复杂任务拆给若干专职 Agent，由编排层协同。工程难点通常不在提示词，而在状态如何共享、流程如何中断恢复，以及成本与延迟能否收敛。以下取舍在多次落地中被反复验证。

## 角色分工的三种基本形态

supervisor-worker 是最常见的形态：编排者负责拆解、派发与验收，子 Agent 只承担单一职能。控制流集中、易于排查，但 supervisor 自身上下文增长最快，容易成为瓶颈。

peer debate 让同层多个 Agent 各自产出方案再交叉评审，适合开放题。它必须配轮次上限和明确的裁定规则，否则会退化成反复互相说服、迟迟拿不出结论。

assembly line 即流水线：检索、写作、审校等环节固定串行。它最可控也最便宜，但上游一旦产出错误格式，问题会沿链路逐级放大，因此每级出口都要有校验。

## 共享状态：黑板与消息传递

黑板（blackboard）模式维护一份全体可读写的共享状态对象，适合字段多、强调整体一致的场景。代价是 schema 演进困难，并发写入需要版本号或归并策略。

消息传递把 Agent 变成近乎纯函数的输入输出单元，便于单测与重放；代价是同一份数据在消息里反复搬运，token 开销上升，排障时也看不到完整现场。

折中做法是混合：计划、证据条目、工具调用记录等结构化字段放共享状态，正文大块文本只传引用，真正需要时再按需注入上下文。

## 流程编排：条件边、检查点与恢复

LangGraph 这类框架把编排建模成状态图：节点是 Agent 或工具，条件边（conditional edge）由路由函数决定下一跳，回跳边天然表达重试与循环。

checkpointer 按 thread_id 把每一步状态快照落盘，是崩溃续跑、人工审核介入、长时暂停恢复的前提。缺了它，重跑一次长流程等于重新烧一遍预算。

终止条件必须显式写进状态。常见做法是把重试计数作为独立字段参与路由判断，并给每一跳加超时，防止两条边互相跳转形成活锁。

## 工具路由：模型决策还是硬编码

硬编码 pipeline 可预测、易测试，但遇到预想之外的问题就失灵；把工具描述交给模型做 function calling 路由更灵活，代价是每轮都要付出工具描述的 token，还会出现漏调、重调与参数捏造。

更稳的是受限路由：先按意图把候选工具收敛到少数几个，再让模型在受限集合里挑，参数通过 schema 校验后才真正执行。

工具契约要单独设计：参数扁平、命名语义清晰、返回结构化且可摘要，切忌把大段原文直接回灌主上下文。

## 成本与延迟预算

成本近似等于轮次数乘以平均上下文长度再乘单价。优先级依次是减少轮次、压缩上下文、按环节分档选型，而不是一上来换更小的模型。

延迟方面，串行链路耗时直接累加。可并行的分支要真并行，流式输出只改善体感，不能掩盖端到端预算红线。

设计阶段就应写死预算：单次请求 token 上限、工具调用次数上限、端到端耗时上限，并在运行时按 trace 统计，超阈值即降级到更短路径。

## 常见误区

- 认为 Agent 越多越好：节点膨胀后协调成本与上下文长度超线性增长，收益反而下降。
- 只调提示词不看拓扑：大量效果问题源于路由条件或状态字段设计不合理，换更强的模型只是推迟问题。
- 跳过 checkpoint：没有快照既无法复现线上故障，也无法实现人工介入后续跑。
- 全量广播状态：结构化摘要配合按需拉取，比把所有中间产物塞进状态更省更稳。
